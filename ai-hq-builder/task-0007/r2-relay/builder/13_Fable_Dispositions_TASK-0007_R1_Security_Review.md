## 1. How Fable verified this, and what Fable deliberately did not do

Per the trail-127 practice, **Fable ran no live adversarial probes for this disposition** — no stub process was started, no request was issued, no exploit was simulated. Verification was static code reading of the 653-line target plus the surrounding artifacts (`09_`, `08_`, the three runbooks, the workflow definitions, `poc/FINDINGS.md`, `selftest_stub.py`, `harness/receipt_conformance.py`, `data/captures/README.md`).

That constraint is a real limitation and is recorded as one: a static reading confirms a defect's *existence and mechanism* but cannot confirm a *runtime* outcome. Where a claim genuinely turns on runtime behaviour it is marked below. In practice the constraint cost little here, because every finding in `12_` is structural and legible in source — and it bought something the live probes did not: the review's 14 probes touched 5 of 13 routes, and reading the whole route table surfaced most of §4.

**The practice worked as intended, in a way worth recording:** independent review found a gate-blocking defect (`SEC-R1-01`) that both the Builder's own adversarial pass and Fable's prior live walkthrough (trail 126) missed — both had tested the *guarded endpoints* and neither had asked whether the guarded thing could be reached another way. That is exactly the failure mode a second, differently-sourced pair of eyes exists to catch, and it is an argument for the owner's open question in trail 127 §5 being settled toward "permanent default."

### 2.1 SEC-R1-01 is not new scope — it is an already-accepted obligation

Recorded so the rework packet does not read as scope creep invented by a reviewer: the substance of SEC-R1-01 is already mandated by `09_` §2 (THE authoritative D3 scenario definition, owner ruling trail 124, verifier-acked in `10_`, corrections applied trail 125). R1P-04 requires a bound idempotency identity **including route/target role**, and its five required tests include *"same task and artifact, different unauthorized target → REJECT, not duplicate-success"*. A service whose side effect accepts anything from anyone cannot run that test. The R1 stub was not asked to implement it — `09_` §4 fixed R1 as scenario-neutral — so this is a **scheduled obligation arriving on time**, not a new demand. The practical benefit: R2 inherits a ready-made, already-verifier-approved acceptance specification instead of one Fable would otherwise invent under time pressure.

## 3. Corrections returned to the verifier

Four items go back with the next relay. Three sharpen the review; one corrects a fix that would damage the round.

- **VC-01 — the SEC-R1-06 illustrative repro does not reproduce.** `metadata: []` is **falsy**, so line 485's `payload.get("metadata") or {}` short-circuits to `{}` and the request returns 200. The defect is confirmed and real, but it requires a **truthy** non-dict (`[1]`, `"x"`, `5`, `true`); probes 10 and 12 in `12A_` plainly exercised one. This is not pedantry: a regression test written to the literal text in `12_` §3 would **pass against the unfixed code**, and this program has already been burned once by a self-test that hid a real defect by exercising the wrong shape (trail 126, the token-lifecycle bug). The required test must name the truthy case.
- **VC-02 — the review's own gate table under-calls its FAIL.** The rows *"Provider decision-field allowlist: PASS"* and *"Provider-supplied decision fields are refused"* are true **at the endpoints probed** and false at service level: `_rejects_provider_decision` is wired to 3 of 13 routes (319, 413, 481). `/poc1/receipt` and `/poc1/refusal` accept an arbitrary object containing `decision`/`approved`/`authorized` and persist it into the same `captures/stub/POC1/` directory, carrying the same `synthetic: true` and `produced_by: stub_server.py` stamps as a genuine owner-decision record (FAB-06). Mandatory refusal 2 is therefore **not** independently verified as a service property. Fable asks the verifier to restate that row.
- **VC-03 — SEC-R1-01's proposed correction, as written, would break POC-3.** `/sink` is not POC-1's endpoint alone: `h_poc3_run_started` hands the same URL out as `stage_endpoint` (502), for a flow that has no case, no owner decision and no ActionRequest anywhere in it. A blanket "single-use capability required, reject replay" rule would fail POC-3 outright and would mis-score a legitimate provider retry — and provider retry behaviour across the mandated mid-flight kill is precisely what POC-3 measures. The capability must be scoped to the POC-1 authorized-relay path, with replay returning the prior receipt and an explicit no-second-side-effect marker rather than a bare refusal, and POC-3's staging path must keep a separate, retry-tolerant identity.
- **VC-04 — neither SEC-R1-05 remedy closes the leak.** Rejecting query components does not help: a secret in the **path** with no query at all (`GET /<secret>`) reaches dispatch, 404s at 560-561, and is still logged verbatim by `_respond` → `send_response` → `log_request`; and a malformed request line double-logs through `send_error` before `do_GET`/`do_POST` is ever entered. The only closing fix is to log a **route-matched constant** (the matched `ROUTES` key, or a literal `<unmatched>`) plus the status, with no caller-supplied substring reaching stderr under any path.

## 5. Rulings

1. **The owner POC session remains BLOCKED**, as the verifier ruled. Fable extends the blocking set: SEC-R1-01..05 **plus** FAB-01..09 and FAB-15. The additions are not security items — they are evidence-integrity items, and the round's deliverable is the evidence corpus. A session run against the current apparatus would produce a corpus that cannot distinguish the two candidates (FAB-02), may silently overwrite itself (FAB-03), and would omit proof of the two properties the POC exists to demonstrate (FAB-01).
2. **The Medium and Low items are corrected in the same round**, not deferred. They are individually cheap, several share a root cause with blocking items, and deferring them would require a residual-risk record and runbook constraints that cost more to write than the fixes cost to make.
3. **No accepted work reopens.** Provider selection, the Release-1 definition (`09_`), the Decision Engine design, the v1.4 baseline, and the production-wrapper architecture (`13B_`) are all untouched by this disposition. This is apparatus rework.
4. **Sequencing: the security rework and the Release-1 scenario re-aim merge into one round, R2.** They were sequential (`09_` §4) on the assumption that R1's endpoints were scenario-neutral. FAB-15 falsifies that assumption: the stub cannot carry `09_` §2's identity tuple, so the re-aim requires endpoint changes *regardless of* the security findings, and the two work items touch the same handlers and the same contract. Splitting them would have the Builder rewrite `h_poc1_review_case`, `h_poc1_verify_decision` and `write_capture` twice and would spend two relay cycles where one suffices. Fable fixes the corrected endpoint contract in the packet (`14_` §2) so the Builder implements against a settled specification rather than discovering it. **This is a PM sequencing call, reversible on the owner's word.**
5. **Fable's role for the re-verification stays narrowed** per trail 127: the corrected stub's adversarial re-verification goes back to ChatGPT as an independent review, with the Builder executing any probes ChatGPT directs. Fable assembles and dispositions; Fable does not run the probes.

## 6. What this costs, in plain terms

The stub was built to be throwaway apparatus and it is being asked to carry more than throwaway apparatus usually does — because in this round the apparatus *is* the instrument of measurement, and a bent instrument produces confident wrong numbers. Nothing here says the Builder did poor work: it found and fixed eight defects in its own build before shipping, and the two mandatory refusals it was asked for both work. What the independent review and this disposition together establish is that the *brief* was too narrow — it asked for two refusals and got them, without asking whether the guarded action could be reached another way, or whether the evidence the apparatus produced would still be readable a day later. That is a Fable defect in `08_`, and it is recorded as one.
